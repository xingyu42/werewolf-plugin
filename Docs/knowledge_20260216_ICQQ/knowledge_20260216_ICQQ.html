🎯 核心摘要 (TL;DR)

一句话：ICQQ 是一个用 Node.js 实现的 QQ 安卓客户端协议库——它不是聊天软件，而是一台"QQ 翻译机"，让你的代码能像真人一样收发 QQ 消息。

认知挂钩：想象你在国外打电话，ICQQ 就是那个同声传译器——QQ 服务器说的是"协议语言"，你的 JavaScript 代码说的是"程序语言"，ICQQ 在中间实时翻译。

"本项目为协议实现，不推荐直接使用。" —— icqq README

这句话至关重要：ICQQ 是底层协议库，不是框架。就像发动机不是汽车——你需要 Miao-Yunzai、Zhin 等框架来包装它。

📖 故事引入：一封被拦截的信

2022 年的某个深夜，takayama-lily 决定归档她的 OICQ 项目——这个让无数开发者能用 Node.js 控制 QQ 的传奇库。社区陷入恐慌："我们的机器人怎么办？"

就在这时，icqqjs 团队 fork 了 OICQ 的代码，像一群接力赛跑者那样接过了火炬。他们不仅修复了登录协议，还加入了频道支持、QQNT 协议和群精华消息——ICQQ 由此诞生。

到 2026 年的今天，ICQQ 已经成为 Miao-Yunzai（云崽）生态的核心引擎，驱动着成千上万的 QQ 群机器人。

2.4 Pick 模式：面向对象的操作入口

// ❌ 旧模式（平铺在 Client 上，已废弃但保留）
client.sendGroupMsg(群号, '消息')
client.setGroupBan(群号, QQ号, 时长)

// ✅ 新模式（pick 出对象，调用对象方法）
const group = client.pickGroup(群号)
group.sendMsg('消息')
group.muteMember(QQ号, 时长)

const friend = client.pickFriend(QQ号)
friend.sendMsg('私聊消息')
friend.thumbUp(10) // 点赞10次

const member = client.pickMember(群号, QQ号)
member.kick()       // 踢出
member.setCard('新名片')
member.mute(600)   // 禁言600秒
为什么这样设计？ 因为旧模式下 Client 类上堆了几百个方法，违反了单一职责原则。Pick 模式将操作分散到 Group、Friend、Member 等对象上，每个对象只管自己的事。

2.7 登录机制：三条路径

graph TD Start["client.login(uin, password?)"] --> Check{"有 uin?"} Check -->|"无"| QR["扫码登录 Watch协议"] Check -->|"有"| Token{"本地有 token?"} Token -->|"有"| TryToken["尝试 token 登录"] Token -->|"无"| HasPwd{"有密码?"} TryToken -->|"成功"| Online["system.online"] TryToken -->|"失败"| HasPwd HasPwd -->|"有"| PwdLogin["密码登录"] HasPwd -->|"无"| QR PwdLogin --> SignAPI{"签名 API 可用?"} SignAPI -->|"是"| Verify{"需要验证?"} SignAPI -->|"否"| Fail["登录失败"] Verify -->|"滑块"| Slider["system.login.slider"] Verify -->|"设备锁"| Device["system.login.device"] Verify -->|"无"| Online Slider -->|"submitSlider"| Online Device -->|"sendSmsCode+submitSmsCode"| Online QR -->|"扫码确认"| Online
⚠️ 真理锚点校准：文档中未充分强调签名 API（sign_api_addr）是登录的硬性依赖。没有可用的签名服务，密码登录将直接失败。这是 2024 年以来腾讯加强安全验证后的现实。

2.8 类继承体系

graph BT Client["Client"] --> BaseClient["core.BaseClient"] Group["Group"] --> Discuss["Discuss"] Friend["Friend"] --> User["User"] Member["Member"] --> User Guild["Guild"] Gfs["Gfs 群文件系统"] Client -.->|"pickGroup()"| Group Client -.->|"pickFriend()"| Friend Client -.->|"pickMember()"| Member Client -.->|"pickGuild()"| Guild Group -.->|".fs"| Gfs Group -.->|"pickMember()"| Member
设计哲学：Friend 和 Member 都继承自 User——因为无论是好友还是群员，本质上都是"用户"。Group 继承自 Discuss（讨论组），因为群就是增强版的讨论组。这种继承关系精确反映了 QQ 的产品演进历史。

🔬 原子级矛盾分析

矛盾 1：协议逆向的法律灰区

ICQQ 的本质是对 QQ 安卓客户端协议的逆向实现。腾讯的用户协议明确禁止使用第三方客户端，这意味着：签名 API 需要频繁更新、账号有被封禁的风险、项目使用 MPL-2.0 许可证而非 MIT。

矛盾 2：OICQ vs ICQQ 的 API 分裂

ICQQ 保留了大量 OICQ v1 的兼容方法（标记为 @Cqhttp），同时推荐使用新的 pick* 模式。同一功能有两种调用方式，新开发者容易混淆。

矛盾 3：QQNT 协议的双轨运行

腾讯正在将 QQ 迁移至 QQNT 架构。ICQQ 通过 NTLogin 和 QQNT 两个标志同时支持新旧协议，但部分 API 行为取决于协议版本。未来旧协议 API 可能失效。

🔍 搜索内化：经验证，OICQ 原仓库已于 2023-11-02 正式归档。ICQQ npm 包名已从 icqq 迁移至 @icqqjs/icqq。当前版本 0.6.10。

4.1 快速开始：5 分钟搭一个回声机器人

const { createClient } = require('@icqqjs/icqq')

// 创建客户端（Watch 协议支持扫码）
const client = createClient({
  platform: 3,
  ver: '2.1.7',
  sign_api_addr: 'http://127.0.0.1:8080/'
})

// 监听上线
client.on('system.online', () => {
  console.log('🎉 登录成功！')
  console.log(`好友数: ${client.fl.size}, 群数: ${client.gl.size}`)
})

// 群消息回声
client.on('message.group', (e) => {
  if (e.raw_message === 'echo') {
    e.reply('🔊 Echo!', true)
  }
})

// 扫码登录
client.on('system.login.qrcode', () => {
  console.log('请扫描 ./data/qrcode.png')
  process.stdin.once('data', () => client.login())
})

📚 温故知新

FAQ

Q1: ICQQ 和 OICQ 有什么区别？
ICQQ 是 OICQ 的 fork。OICQ 于 2023-11 归档停止维护，ICQQ 继续维护并添加了：频道支持、QQNT 协议、群精华消息、ForwardElem 消息类型、指定群/好友监听等功能。API 基本兼容。
Q2: 为什么密码登录总是失败？
99% 的原因是签名 API 不可用。自 2024 年起，腾讯加强了协议签名验证，必须配置 sign_api_addr 指向一个可用的签名服务。
Q3: pickGroup 和 client.sendGroupMsg 有什么区别？
功能相同。pickGroup().sendMsg() 是新版推荐方式（OOP 风格），client.sendGroupMsg() 是旧版兼容方式。新代码应一律使用 pick 模式。
Q4: 如何处理滑块验证码？
监听 system.login.slider 事件，获取验证 URL，通过浏览器或第三方工具获取 ticket，然后调用 client.submitSlider(ticket)。Miao-Yunzai 内置了自动获取机制。
Q5: ICQQ 支持 QQNT 吗？
部分支持。Client 有 NTLogin 和 QQNT 两个标志位，默认 true。NT 版本下部分 API 行为不同（如聊天记录数量不受 20 条限制、图片获取用 getNTPicURL 系列）。
Q6: 如何发送合并转发消息？
使用 makeForwardMsg 制作，然后 sendMsg 发送。注意好友图片和群图片格式不同，跨场景发送可能裂图。
Q7: 账号会被封禁吗？
存在风险。降低风险的做法：避免高频操作、使用正确的协议版本、保持签名 API 更新、不要频繁切换登录设备。
Q8: 如何获取 Cookie 和 bkn 来调用 Web API？
登录成功后自动获取：client.cookies[domain] 获取 Cookie，client.bkn 获取 CSRF Token。支持 qun.qq.com、vip.qq.com 等 20+ 域名。
